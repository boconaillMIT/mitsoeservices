## Owner-private encrypted person notebooks

The notebook is separate from shared account notes. The real signed-in identity and effective identity must match an explicitly enrolled owner (`tara1013` or `oconaill`), with current `finance:aeroastro` access. The repository owner is derived on the server from that identity; administrators can open only their own notebook, never select another owner. Administrators have no private-notebook override, including when using a view-as label. Current read permission allows unlocking; current write permission additionally allows setup and append. Every request rechecks the owner and grant before loading storage. No private note content appears in the ordinary roster response, shared notes, exports or printing.

Tara sets a unique notebook passphrase of at least 20 characters, separate from MIT credentials. WebCrypto PBKDF2-SHA256 (600,000 iterations, random 32-byte salt, NFC normalization) derives a non-extractable wrapping key. A random AES-256-GCM data key is wrapped locally. The server receives only the wrapped key and client-encrypted note envelopes, with fresh 96-bit IVs and 128-bit authentication tags. Authenticated data binds notebook, owner, stable person key and note UUID. Decryption keys and readable notes remain in page memory; no browser persistent storage is used. The notebook locks on leaving the tab, printing, pagehide or ten minutes of inactivity. Locking preserves pending drafts only as ciphertext in page memory; leaving the page discards unsaved drafts. Author and timestamp metadata are supplied by the server.

The owner passphrase is not recoverable by this site. Configuration and notes are immutable unique-key records, with idempotent retry and no overwrite/reset endpoint. Storage uses separate QuickBase scope `aeroastro-private-tara1013`, keys `aeroastro-private:v1:tara1013:*`, plus the existing service encryption layer. Possession of the service key does not decrypt note contents. Metadata (owner, time, person association, approximate length) remains available to infrastructure operators. This protects stored content; a compromised browser/device or an operator who maliciously changes delivered JavaScript could capture future secrets. Do not describe this as protection against active control of the hosting platform.

Person associations never use spreadsheet row numbers or email alone. An encrypted identity-map snapshot `aeroastro-finance:person-identities:current` binds each appointment row to an HMAC-SHA256 person key, derived locally from its original MIT ID using an HKDF-separated purpose key. Raw MIT IDs are not stored in this notebook identity map or private note envelopes. The MIT employee ID is separately available as an explicitly requested HR roster field to authorized finance users. Match its source hash exactly to the roster before using it. Multiple appointments for the same person share one key; mismatched or missing maps fail closed and preserve all existing notes. Every roster refresh must regenerate and verify this map from the matching original under the same identity derivation key before enabling note links. Preserve the identity derivation key across service-key rotations, or explicitly migrate the encrypted mapping; do not silently generate different identities.

## Direct Warehouse refresh

The desktop helper in `tools/aeroastro_warehouse.py` connects directly to MIT Oracle in native-client mode using the current user’s Warehouse password. It runs a single read-only transaction with fixed queries; it accepts no supplied SQL or server URL. A one-time per-user Windows protocol registration (`--install`) lets the accounts-page button open the helper. Python 3.12 with python-oracledb and a compatible MIT Oracle client are prerequisites. No Warehouse password is saved, sent to Netlify/QuickBase, or included in process arguments. The password is entered only into the local helper prompt and sent to MIT Oracle.

The site issues a 15-minute, actor/source-version-bound authorization after checking AeroAstro finance write permission and same-origin JSON. The helper validates that authorization with the fixed HTTPS site endpoint before requesting a password. The server checks current permission and feature visibility again on job retrieval and upload. Replayed jobs, stale data, revoked grants and mismatched fiscal periods cannot overwrite the current source.

Both queries and upload validation restrict results to the previously verified AeroAstro account inventory and profit-center whitelist. Complete inventory coverage is required. New accounts and ownership changes require a separate verified inventory update. The first implementation supports up to 999 verified accounts (the current inventory has 755); it stops before querying if this is exceeded.

Balances come from BALANCES_SUMMARY; current/summer GL expenses come from SUMMARY_STATEMENT_DETAIL and GL_ACCOUNT_REPORT. Complete GL expense totals must reconcile to the balance summary before any shared update. The server derives academic-year faculty/TA/tuition patterns and corresponding faculty benefits. Balances and the matching profiles are saved together inside the same encrypted, version-checked QuickBase account snapshot, so a reader cannot see a new balance with an old forecast. Existing notes, exceptions, HR sources, private notebooks and permissions are untouched. Legacy separate expense-profile snapshots remain available for older account sources; an embedded matching profile takes priority.
