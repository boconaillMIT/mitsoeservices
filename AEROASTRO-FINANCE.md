# AeroAstro finance workspace

## Tara's encrypted private person notebook

The notebook is separate from shared account notes. Both the real signed-in identity and effective identity must be `tara1013`, with a current `finance:aeroastro` grant. Administrators have no private-notebook override, including when using a view-as label. Current read permission allows unlocking; current write permission additionally allows setup and append. Every request rechecks the owner and grant before loading storage. No private note content appears in the ordinary roster response, shared notes, exports or printing.

Tara sets a unique notebook passphrase of at least 20 characters, separate from MIT credentials. WebCrypto PBKDF2-SHA256 (600,000 iterations, random 32-byte salt, NFC normalization) derives a non-extractable wrapping key. A random AES-256-GCM data key is wrapped locally. The server receives only the wrapped key and client-encrypted note envelopes, with fresh 96-bit IVs and 128-bit authentication tags. Authenticated data binds notebook, owner, stable person key and note UUID. Decryption keys and readable notes remain in page memory; no browser persistent storage is used. The notebook locks on leaving the tab, printing, pagehide or ten minutes of inactivity. Locking preserves pending drafts only as ciphertext in page memory; leaving the page discards unsaved drafts. Author and timestamp metadata are supplied by the server.

The owner passphrase is not recoverable by this site. Configuration and notes are immutable unique-key records, with idempotent retry and no overwrite/reset endpoint. Storage uses separate QuickBase scope `aeroastro-private-tara1013`, keys `aeroastro-private:v1:tara1013:*`, plus the existing service encryption layer. Possession of the service key does not decrypt note contents. Metadata (owner, time, person association, approximate length) remains available to infrastructure operators. This protects stored content; a compromised browser/device or an operator who maliciously changes delivered JavaScript could capture future secrets. Do not describe this as protection against active control of the hosting platform.

Person associations never use spreadsheet row numbers or email alone. An encrypted identity-map snapshot `aeroastro-finance:person-identities:current` binds each appointment row to an HMAC-SHA256 person key, derived locally from its original MIT ID using an HKDF-separated purpose key. Raw MIT IDs are neither stored in this map nor returned to browsers. Match its source hash exactly to the roster before using it. Multiple appointments for the same person share one key; mismatched or missing maps fail closed and preserve all existing notes. Every roster refresh must regenerate and verify this map from the matching original under the same identity derivation key before enabling note links. Preserve the identity derivation key across service-key rotations, or explicitly migrate the encrypted mapping; do not silently generate different identities.

Pages: `/units/aeroastro/finance/accounts` and `/units/aeroastro/finance/people`.

`finance:aeroastro` is a separate permission. Read permits the finance and personnel views. Write additionally permits append-only account notes; it never permits changes to balances, salaries, positions, appointments or permissions. A unit-wide AeroAstro grant alone does not expose this additional personnel view. Only School-wide administrators inherit this scope; other School users require an explicit grant. Ordinary AeroAstro navigation requires the corresponding unit grant. Keep other unit and RCT permissions separate.

The API checks this scope on every request. Direct function routes have the same protection. Account note POSTs require same-origin JSON, a UUID operation ID and an account on the approved AeroAstro snapshot/inventory. Author and timestamp are supplied by the server. Each note is an immutable, individually encrypted QuickBase snapshot-table record with a unique key; no read/modify/write replacement of the entire notes list. Optional source labels let authorized users identify information from emails, meetings or other documents without implying that the source authored their note.

The independent `aeroastro-finance` visibility flag does not unlock the older account-review pilot, which may remain hidden. Grant Tara only `aeroastro:read` and `finance:aeroastro:write` as requested, preserving every other user's grants. Deploy and verify all new policy-aware functions before saving the new scope grant. To roll back to a release that predates this scope, remove only the newly introduced finance grants first; older policy validators do not recognize this scope. Do not restore an entire old policy over intervening permission changes.
